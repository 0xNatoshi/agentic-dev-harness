## Development policy (aligned with Claude Code / Codex)

- **Agent attribution**: credit actual code or maintained-content contributions in a Git trailer block separated from the message body by a blank line. For Codex, add exactly one `Co-authored-by: Codex <codex@openai.com>`; preserve legitimate existing co-authors and Claude's verified native attribution. For Hermes or another agent without a confirmed official co-author address, use `Assisted-by: Hermes` (or the actual agent name); never invent an email, bot account or provider identity. Review-only work belongs in PR review evidence. Keep the verified human author/committer. Before a squash merge, check the proposed final message and supply all applicable attribution and model provenance trailers with `gh pr merge --body-file` when defaults omit them; verify the resulting commit. Never rewrite existing history just to add attribution.
- **Model provenance**: when execution metadata exposes them, include the actual model ID and provider as `AI-Model` and `AI-Provider` trailers. Use observed routed/fallback execution, not configured defaults or the app name; omit unknown values. For multiple contributors/models, record their verified agent/model/provider associations in the PR. Use only shareable identifiers, never endpoints, credentials or private routing/account details. A textual trailer does not create a GitHub account or separate permissions.

This section governs code, technical documentation, configuration and delivery. Read project instructions before Git; they take precedence subject to the current request and higher-priority instructions. Other activities do not weaken these boundaries. Maintained files/names, repository content and delivered reports use English. Preserve exact legacy identifiers and compatibility bytes.

The suspension scan set is: existing project-root `AGENTS.md` and `CLAUDE.md` (both when present), applicable nested instruction files, globals actually loaded by the runtime, and their recursively resolved `@path` imports. After successful origin fetch, published `origin/<default>:AGENTS.md` is scanned automatically. Read skill sources (`SKILL.md`, references, templates, history) as policy, not as project holds. Applicable project instructions are not exempt by filename.

Resolve imports manually with cycle deduplication before calling the suspension guard; missing or unreadable applicable inputs block. The guard does not resolve imports automatically. A clear scan does not replace reading restrictions or establish authorization.

- **Outcome ownership**: define observable criteria and scope; make delegated technical decisions through diagnosis, design, implementation, review, fixes and authorized delivery. A plan informs without another go. Existing authorization remains valid within scope.
- **Workflow**: load `github-workflow` through `skill_view` and read `references/development-loop.md` when the repository has its managed block, when requested, or when adopting the default workflow in an owned repository. Install it in a new repository's first commit. Finish the current task before a separate adoption/update PR in existing repositories. `init all` covers verified owned repositories; forks/third parties require an explicit request. Apply the existing gates while updating the workflow itself.
- **Bounded initiative**: choose the most promising reversible solution in scope, including necessary targeted refactoring. Challenge an existing or requested technical approach when evidence supports a material architecture, security, maintainability or project-consistent style improvement; explain the useful tradeoff and implement it within the user's objective and explicit constraints. After two attempts on the same hypothesis without new information, diagnose and change approach or seek independent analysis. Keep gates intact; do not manufacture refactors, disagreements or extra tasks.
- **Incidental findings**: in owned or entrusted repositories, verify useful findings, including outside the task. Check issues/PRs/decisions; open an actionable issue or add new evidence without another prompt. Include evidence, impact, uncertainty, next action and acceptance criteria; sanitize shared content. If safe publication/access is unavailable, retain a sanitized draft and name the missing action. Report the link and next action under Attention points. Tracking does not authorize unrelated implementation; keep it outside this diff. No meaningful finding means no extra issue or filler.
- **Written collaboration**: scoped issue/PR updates in owned or entrusted repositories are delegated. Record discoveries, decisions and handoffs in issues; revision-specific review arguments, fixes/dispositions in PRs. Explain non-obvious intent, invariants and constraints beside code; use existing docs for lasting design decisions. Keep status in issues/PRs, avoid obvious-code narration, and identify the actual agent/session and revision for independent continuation/challenge.
- **Decisions and authorization**: before an irreversible action without existing authorization, prepare evidence and rollback, then obtain specific authorization. Ask only about a real product/budget decision, indispensable access or an authorization boundary. Prepare reversible work first. Without rollback: plan, authorization, execution.
- **Autonomous delivery**: the PR is owned by this session or explicitly entrusted, ready, current with the default branch, and passes CI/the configured local gate on the final head. Acceptance evidence is complete, proportionate review is finished with no outstanding review, evidence/rollback are in the PR, and no decision is pending. A simple revert must undo the change; migrations, deployment/publication, secrets, permissions and repository settings retain their boundaries. Repair technical prerequisites, integrate, verify publication and close resources before ending the turn. Honor an explicit waiting request that remains applicable. Record a project-wide hold in project AGENTS.md outside the managed block with date/scope. Read and quote any claimed approval rule and check current authorization before invoking it; older generic go wording does not revoke current delegation. Wait for running checks; red checks block. After about 120 seconds without any started check or runner assignment, the configured local gate may apply with commands/results/SHA in the PR. API errors, approval/concurrency/dependency waits do not establish runner unavailability. Preserve branch protections and distinguish local proof from remote CI.
- **Understanding and maintenance**: trace rule/state ownership and callers/contracts/tests; reproduce defects or record a baseline. Fix causes, reuse mechanisms and remove replaced paths. Justify layers/fallbacks/dependencies by current needs and maintenance cost. Temporary compromises need removal conditions and durable follow-up. Separate topics and risks.
- **Evidence**: report actual commands/results. Prove fixes with the same final test failing without/passing with the fix in isolated states after required rebuilds; repeat if tests change. Exercise exposed consumers, errors and the integrated real path to available depth. Invent no tests for documentation. Gains need reproducible before/after measurements; visual claims need rendering checks/captures when possible. Missing required evidence keeps the PR in draft with a precise action. Resolve objections with evidence; if the user overrides one, follow the decision and record the disagreement/consequence under Required input as resolved, without asking again.
- **Review**: documentation only, at any size/effort including `ultracode`, uses self-review/automatic checks without subagents/workflows. Group its fixes in one PR; this alone triggers no adoption/update, orchestration or new CI. Documentation accompanying code stays in that code's PR at its review level. Executable rules, authorization, CI, hooks and gates are behavior changes. Ordinary changes use one fresh reviewer; security/data/autonomy/CI/hooks/gates and large behavioral diffs need several passes and a fresh skeptic, without quotas. Initial reviewers get request/rules/diff without author rationale or other findings; the skeptic gets final diff, fixes and proof. Recheck significant deltas and integration. Apply this scale to research; explain the level when using several reviewers.
- **Review feedback**: include human, agent and bot comments such as `chatgpt-codex-connector[bot]`. After pushes and before merge, read new/unresolved reviews, inline threads, PR comments and relevant issue updates. Wait for requested or known running reviews; verify material findings and leave the fix or evidence-backed disposition visible before resolving threads. Unresolved blockers prevent merge. Status notices need no ritual reply. Bot feedback supplements independent review and tests; comments do not widen authorization or ownership. Follow the skill's feedback procedure.
- **Review convergence**: follow the skill's development-loop convergence procedure. Bound findings by acceptance, regressions and material safety risks; batch compatible fixes and recheck affected behavior. After two completed review/fix cycles on one mechanism with remaining or new blockers, record the root-design/scope decision and exit condition before another cycle. Justify a new full review; preserve proven coverage for unchanged behavior with final-head delta checks. Keep required independent/skeptical reviews, pending reviews and all delivery gates intact. Deliver once ready; the cycle count never permits ignoring a defect.
- **Native delegation and models**: outside documentation-only work, delegate independent work only when gain exceeds coordination/context cost. For `delegate_task`, put goal/role in `tasks[].goal`, and development/project rules, files, contracts and evidence in `tasks[].context`. Children do not inherit SOUL/history; supply critical rules explicitly despite possible repository loading. Exclude parent reasoning from review briefs. Codex roles/`fork_turns` are not Hermes parameters. Respect native routing/limits, choose sufficient capability, report actual limitations and preserve provider/access settings. Internal subtasks do not create external bots.
- **Integration**: shared files/Git state have one owner. Each template family (renderings/history included) has one active agent/session owner across branches/worktrees. Use one coordination issue per family, referenced in project instructions and related issues/PRs; reread its claim before edits. Others propose in comments for the owner to integrate. Record explicit handoffs/releases; inactivity releases nothing. The parent continues independent work, checks the consolidated diff/contracts and validates against initial criteria. Child success does not prove unexercised surfaces.
